# Bad Game Pickleball Courts

A responsive web app for organizer-run open play and one-day events. Players request a place from a shared link; organizers approve requests, manage attendance, configure each court, and record match results. The app uses Firebase Hosting, Authentication, and Cloud Firestore. It does not use SQLite.

## What it does

- Dated session with an adjustable player limit (32 by default). Signup links allow advance requests and expire at midnight in Manila after the selected date. Approved reservations hold spots before check-in. Later approvals go to a waitlist; a removed or checked-out reservation promotes the oldest waitlisted player.
- Public signup for an existing player profile or a new profile with name, skill level, division eligibility, and optional photo. All public requests require organizer approval. Existing-profile claims are also reviewed.
- Approved profiles appear in a limited public search directory that supports first-name, full-name, and surname prefixes; full player records stay in the organizer database.
- Organizer check-in, check-out, rejection, removal, directory search, profile editing, and daily reset. Reset preserves player profiles and past results and creates a new signup link.
- Reusable courts with separate skill eligibility, open/mixed/women/men divisions, and singles/doubles format. Each court can draw and start independently. One player cannot be on two active courts.
- Winner recording adds one win to each winner and one loss to each opponent. Results can be saved only once. The dashboard shows player records and recent results.
- One-day events have their own signup link, approval queue, player limit (up to 512), check-in, and waitlist. A fixed doubles team reserves two spots together or waits together. Organizers can add people directly, create teams manually, or draw teams once.
- Tournaments support singles or doubles, single elimination with automatic byes, or round robin with a final. Larger round robins use pools. Rotating-partner doubles rank individuals and put the top four into a final; the winning pair share the title.
- Organizers assign and start each tournament match on a court, record best-of-1 or best-of-3 scores, correct results with an audit trail, and publish standings and champions. Each completed match counts once toward lifetime wins and losses. The optional prize field is a record only; the app does not process payments.

## Firebase setup

The web config for project `bad-game-pickleball` is in `src/firebaseConfig.js`. This config identifies the Firebase web app and is intended to be public. **Keep service account JSON files private; never put one in `public/`, `src/`, Git, or Hosting.** The repository ignores common service account filenames.

In [Firebase Console](https://console.firebase.google.com/project/bad-game-pickleball/overview):

1. Create the **Cloud Firestore** database if it is not already created. Choose a location near your players. The rules in this repository replace temporary setup rules at deployment.
2. Under **Authentication → Sign-in method**, enable **Anonymous** for player signups. Enable either **Google** or **Email/Password** for organizers. Add your Hosting domain to authorized domains if Firebase asks for it.
3. Create the first organizer's Authentication account. For Google sign-in, signing in once from `/admin` creates the Auth user, even though access is refused until the next step. For email/password, create the user in Firebase Console.
4. In Authentication → Users, copy that user's **UID**. In Firestore, create `organizers/{UID}` with an `active` boolean field set to `true`. Only a project administrator or the Admin SDK can create this document; web clients cannot grant themselves organizer access.
5. If using the Admin SDK instead of the Console for step 4, set `GOOGLE_APPLICATION_CREDENTIALS` to the private service account file on your machine and run `npm run bootstrap:organizer -- organizer@example.com`. The account must already exist in Firebase Authentication.

Photos are compressed to small JPEGs and stored in Firestore with the profile. This avoids requiring Cloud Storage billing for this first version. Approve only real people: the public link is shared with the group, and anonymous accounts can still submit pending requests until the organizer reviews them.

## Run locally

Requires Node.js 20 or newer. The Firestore emulator also requires Java 21 or newer.

```powershell
npm install
npm run dev
```

Open `http://localhost:5000/admin` for the organizer dashboard and `http://localhost:5000/events-admin` for events. The web app automatically uses the local Auth and Firestore emulators at that address. Emulator data is temporary unless you export it. Player signup pages need a link generated by an organizer.

Run the domain, Firestore rules, signup/court, and event lifecycle tests with:

```powershell
npm test
```

Use `npm run test:unit` for a quick domain-only check without Java. CI and deployment scripts run the full test suite.

## Deploy

The prior player/session migration and baseline rules rollout are complete. For a fresh project, run the migration dry run and apply steps before its first deployment. Sign in to Firebase CLI with an account that can manage project `bad-game-pickleball`, or set `GOOGLE_APPLICATION_CREDENTIALS` to a private service account file for the Admin SDK rules command.

```powershell
npm ci
npm test
node scripts/migrate-firestore.mjs --dry-run
# On a fresh database only: node scripts/migrate-firestore.mjs --apply
npm run build
node scripts/deploy-firestore-rules.mjs
npx firebase deploy --only hosting --project bad-game-pickleball
```

The migration adds expiry and search fields, updates the limited public directory, and reconstructs entry match summaries while retaining history. A second migration dry run should report zero changes. This app's current queries do not require composite indexes. Deploy rules before Hosting so event signup and public results work as soon as the new pages go live. The expected Hosting address is `https://bad-game-pickleball.web.app`.

The signed-in CLI account or service account must have project access. The Firebase web config identifies the app but does not grant deployment permission.

`npm run deploy:rules` uses the Admin SDK and verifies the live rules. `npm run deploy:hosting` runs the test suite, builds the pages, and deploys Hosting. Never commit the service account JSON file.
